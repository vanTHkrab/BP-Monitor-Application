# BP Monitor — mobile app

Expo + React Native app for patients and caregivers. Logs blood-pressure
readings, photographs the monitor, and runs an on-device model to check the
framing before the shutter fires.

This is the product. `web/` is an internal dashboard, not a second client.

Offline-first: a reading is saved locally and shown immediately, then
reconciled with the server. The app is expected to work with no signal.

## Quick start

```bash
# from client/
pnpm install
pnpm start          # Metro — runs verify-models first via the prestart hook
```

Point it at a gateway before the first run. `client/.env`:

```bash
# Your machine's LAN IP — a physical device cannot reach the dev
# machine's loopback. The /graphql path is required.
EXPO_PUBLIC_API_URL=http://192.168.1.20:3000/graphql
```

Unset, `src/services/endpoint.ts` derives the host from Expo and throws if it
cannot. Full setup: [docs/guides/setup.md](../docs/guides/setup.md).

## Commands

```bash
pnpm start           # Metro
pnpm android         # native build + install
pnpm ios

pnpm check           # ⬅ the gate: lint → typecheck → verify-graphql → test:unit
pnpm lint            # --max-warnings 0: a warning fails like an error
pnpm typecheck       # tsc --noEmit
pnpm verify-graphql  # validate src/ operations against the gateway schema
pnpm test:unit       # functions, hooks, stores, lint rules, build scripts
pnpm test:screens    # whole-screen renders — NOT part of check
pnpm test            # both halves

pnpm verify-models   # sha256 of bundled models vs the ai-service manifest
pnpm sync-yolo-model # refresh the bundled model copies
```

`pnpm check` is most of what "done" means — see [AGENTS.md](./AGENTS.md) for
why the order of those four steps is load-bearing.

**It is not all of it.** `check` runs `test:unit` only, so a green check does
not mean the screens render; run `pnpm test:screens` before calling a change
to anything under `src/app/` done, and `pnpm test` before shipping. CI runs
both. `verify-models` and `expo-doctor` sit outside `check` as well.

## Layout

```text
client/
├── app/                    # expo-router routes — file-based
├── src/
│   ├── modules/            # feature modules: readings, capture, auth, caregiver…
│   ├── services/           # GraphQL transport, endpoint resolution, uploads
│   ├── database/           # SQLite: the offline outbox and the confirmed mirror
│   └── lib/                # shared helpers
├── modules/bp-vision/      # native Kotlin Expo module — YOLO, CRNN, CameraX
├── assets/models/          # yolo11n.onnx + crnn.onnx (tracked; hash-checked)
├── android/                # generated by prebuild — untracked, keep it that way (AGENTS.md)
├── scripts/                # verify-models, sync-yolo-model, verify-graphql
├── __test__/screens/       # whole-screen render tests (outside src/)
├── app.json                # Expo config — plugins, permissions, googleServicesFile
└── eas.json                # EAS build profiles: development, preview, production
```

## Environment variables

| Variable | Required | Description |
| --- | --- | --- |
| `EXPO_PUBLIC_API_URL` | Effectively yes | Full gateway GraphQL URL, path included. Falls back to Expo's LAN-host derivation, which fails on a device |

`client/.env` is gitignored, and EAS uploads only what git can see — so a
`preview` or `production` build gets **none** of the above from your machine.
Those two profiles read from an EAS environment of the same name instead
(`environment` in [`eas.json`](./eas.json)). If one is empty, the build
succeeds and then throws on the first GraphQL call, because a standalone binary
has no Expo host to fall back to. `development` is exempt — a dev client gets
the host from Metro.

Check with `eas env:list --environment <name>` rather than assuming; this is
EAS-side state that changes without a commit. See
[push-notifications-setup.md](../docs/guides/push-notifications-setup.md).
