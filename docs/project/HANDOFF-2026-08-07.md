They were audited by `deep-research` before merge, which found **twelve false
claims** — including one that told two agents a newly added e2e spec would not
run, when in fact it runs by default against a live Supabase instance holding
real patient rows. Assume the same rot is possible again: an agent definition
is a worse place for a false claim than a doc, because a human reading a wrong
doc usually notices and an agent acts on it.

## What to pick up next

In this order, and the order is argued rather than conventional.

**1. `graphiql`'s env gate has no test.** One line in `app.module.ts` decides
whether a mutation-capable schema explorer is served against live patient data.
`nest-reviewer` confirmed an inverted-gate mutant survives the whole suite. It
sits in the same options object the new `app.module.spec.ts` already resolves,
so the scope is small — the cost is that the ternary evaluates at module load,
so covering it needs `jest.resetModules()` and a re-import per case rather than
a plain read. **Smallest change, largest consequence if wrong.**

**2. `I-003` — the push build config.** The repo-side config has since landed;
what remains is blocked on Firebase Console access, so it needs a human. Worth
doing early anyway: it is the difference between a feature that exists and a
feature that works, and everything else about it is already merged and tested.
Follow [push-notifications-setup.md](../guides/push-notifications-setup.md),
which also records the defect found while landing the config: `client/android/`
had been committed despite being gitignored, which made EAS resolve the project
as bare and skip prebuild — so `android.googleServicesFile` would never have
been applied. It has been untracked; the guide says how to spot it recurring.

**3. Tier 1 of [TESTING-plan.md](./TESTING-plan.md) — config contract checks.**
Assert that a variable Compose sets is a variable the code reads. A day's work,
no infrastructure, and it closes the class that produced the two worst defects
found this session.

**4. Tier 2 — make the gateway's e2e suite actually run.** The specs exist. The
work is a disposable Postgres. **Read the warning in that document first**: the
guard is per-file and `test/app.e2e-spec.ts` does not have it, so a new spec
runs by default against whatever `DATABASE_URL` points at.

**5. `A-010` is a decision, not a ticket.** Whether a caregiver may edit their
patient's name. FR-01.3 asks for it; it was deliberately excluded because a
name is how other people identify the patient rather than health data — the
same judgement that excluded `email` and `phone`, which are unique sign-in
identities. This one goes to the team, not to an agent.

## The lesson worth carrying, not just the tasks

Five defects were found this session that had shipped or were about to. Not one
was reachable by a unit test, and two were structurally unreachable.

Every one of them lived at a **boundary between two systems** — Compose and
code, image and filesystem, Markdown and renderer — and every one was found by
inspecting the **artifact** (the resolved config, the built image, the rendered
HTML), never the unit.

And every one failed **silently, on a path deliberately built to survive
failure**. A graceful-degradation branch is a good design and a bad alarm: a
misconfiguration that lands on it looks exactly like the condition it was
written for. The question that found them was not "does this pass" but **"how
would anyone know if this were wrong?"**

The same pattern appeared in the documentation. Repeatedly, a comment or a doc
described a design the code had abandoned — a data model replaced, a file
deleted, a consumer that never read the thing it was named as reading. Those
are not cosmetic: this session watched a wrong comment get copied into a new
test, and watched a wrong agent instruction point at a live database.

## Traps

Not repeated here — see **Known constraints a future session will hit** in
[TESTING-plan.md](./TESTING-plan.md), which covers the gateway's `pnpm test`
missing `--watchman=false`, its six pre-existing lint errors, `expo-doctor`'s
patch drift, and `DATABASE_URL` pointing at a live Supabase instance.

One more, learned the hard way and not recorded there: **an untracked file
follows you across a branch switch, and `git add -A` on the next branch will
commit it.** A 301-line spec written on one branch ended up inside an unrelated
commit on another. Check `git status` before staging, not after.
